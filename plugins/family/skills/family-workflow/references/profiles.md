# The four profiles

The stages never change; their depth does. Pick the profile that matches who is doing the work, and say which one you are running — a run that mixes profiles by accident is the failure this file exists to prevent.

Each profile has its own skill with the full procedure. Read this file to choose one; read the skill for how to run it.

| Profile | Who | Depth | Skill |
| --- | --- | --- | --- |
| Solo | one person, all six stages | light, no stage skipped | `solo-development` |
| Developer | one developer inside a team | owns Frame, Architect, Make, Yield; hands Inspect and Launch | `developer-workflow` |
| QA | the QA role | owns Inspect in depth; pushes acceptance back into Frame and Architect | `qa-workflow` |
| Team | the whole team | all six stages, a named owner and a handoff contract between each | `team-workflow` |

- **Solo** — the missing second opinion is the problem; the stage agents replace it. Read `solo-development`.
- **Developer** — the ticket is not a frame, and review is not a formality. Read `developer-workflow`.
- **QA** — testability is decided at Frame and Architect, and a repeated defect becomes a check. Read `qa-workflow`.
- **Team** — ownership without a handoff is where work stalls. Read `team-workflow`.

## Choosing

- One person, no team: **solo**.
- A developer with reviewers and a release owner: **developer**.
- The person accountable for acceptance and the go/no-go: **QA**.
- Setting up or fixing the process for several people: **team**.

A team running a lighter profile for a slice is a decision; say so in the frame so it can be challenged. The stage definitions themselves are in `references/stages.md`; the depth for each profile is in the skill named above.
