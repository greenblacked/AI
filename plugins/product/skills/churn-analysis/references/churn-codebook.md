## Codes and their evidence

Assign one primary code per account and at most one secondary. The primary code is the
reason without which the account would most likely have stayed. Adapt the codes to the
product, but keep the set small (about ten) and fixed for the period, so counts compare.

| Code | Controllable | Evidence that points to it | Often confused with |
| --- | --- | --- | --- |
| Never activated | yes | Setup never finished; core action rarely or never used in the first 60 days | Price or value (the product was never in use to be worth anything) |
| Usage declined | yes | Core usage falling for 60 or more days before the decision, no single trigger | Champion left (check whether the decline starts when a person goes quiet) |
| Champion left | partly | The main user or buyer stopped logging in or left the company; a new contact asks basic questions | Usage declined |
| Missing capability | yes | Tickets or notes naming a specific gap; a requested feature with a deadline | Moved to competitor (the competitor is often where the capability was found) |
| Moved to competitor | partly | Named competitor in notes, data export shortly before cancelling | Missing capability, price |
| Reliability or quality | yes | Incidents or severe bugs affecting the account in the 90 days before; complaints about errors | Support experience |
| Support experience | yes | Long resolution times, reopened tickets, escalations | Reliability |
| Price or value | partly | Explicit price discussion with a usage level that justifies the comparison; a cheaper plan requested and refused | Never activated, usage declined |
| Budget or business distress | no | Layoffs, funding problems, spending freeze named; cuts across many vendors | Price or value |
| Acquired, merged or closed | no | Ownership change, consolidation onto the acquirer's tools, business closure | Moved to competitor |
| Involuntary | yes, through dunning | Payment failed and was not recovered; no cancellation request | (Analysed separately, not coded here) |

Quote or reference the evidence rather than summarising it, so a second reader can
check the code without re-reading everything.

## Second-coder check

1. A second person codes about 20 accounts from the sample without seeing the first codes.
2. Compute the share of accounts where the primary codes match. As a working rule, below
   about 80% means the codebook is not yet reliable enough to report from.
3. For each code involved in disagreements, read the disputed accounts together and
   tighten the code's definition or its distinguishing evidence.
4. Recode the whole sample with the revised codebook.

## Comparing with the dropdown

Cross-tabulate the dropdown answer against the primary code. The usual finding is that
"price" or "not using it enough" in the dropdown splits across several coded reasons.
Report that table: it is the evidence for why the dropdown should not drive decisions,
and it shows which dropdown options could be reworded to collect better data.
