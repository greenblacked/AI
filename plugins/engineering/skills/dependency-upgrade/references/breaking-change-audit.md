# Breaking-change audit

How to turn an upstream changelog into a list of changes that apply to code you actually
have, and how to find each one in a codebase rather than waiting for the test suite to
find it for you.

## Contents

## Classes of breaking change, and how each one is found

Order the list by how late the change would otherwise be found. The first two rows cost
minutes; the last two are the ones that reach production.

| Class | Example | Found by |
| --- | --- | --- |
| Removed symbol | A function, class or module deleted | The compiler, the type checker, or an import error at load |
| Changed signature | A positional argument became keyword-only, a parameter was removed | The compiler or type checker, in typed languages; a runtime error otherwise |
| Changed default | Retries went from 3 to 0; strict mode became the default; a cache became opt-out | Nothing. You have to read and then grep |
| Changed semantics | A sort became unstable, an error is thrown rather than returned, a date parse became stricter, a timeout gained a finite value | Nothing, unless a test happened to assert on it |
| Changed output shape | An extra field in a serialised payload, a different key order, a new error code | A consumer, usually a different team's |
| Dropped platform support | The new major requires a newer runtime, libc or OS | The build, if you build on the same platform you deploy to; production if not |
| Peer or transitive constraint change | The new major requires a peer you cannot yet move | Dependency resolution, loudly, which is the good case |

The two "found by nothing" rows are the whole reason this audit exists. Everything else
is discovered by machinery you already run.

## Reading a changelog for what it under-reports

Upstream reports what it considers breaking. Its definition and yours differ in three
predictable places.

- **Bug fixes are breaking if you depended on the bug.** A fix that corrects rounding,
  ordering or an off-by-one is listed under "Fixed" and changes your output. Read the
  fixed section with the same attention as the breaking one.
- **Performance changes are not listed as breaking.** A rewrite that halves memory can
  double p99 for your access pattern, and a lazily-evaluated result that became eager
  changes when errors surface. If you have capacity assumptions tied to this dependency,
  they are now unverified.
- **Deprecations in the *previous* major are removals in this one.** The migration guide
  for N usually assumes you cleared N-1's warnings. If you did not, its instructions will
  not match your code.

Where the changelog is thin, the commit log between tags is not:

```bash
git clone --filter=blob:none https://github.com/org/pkg /tmp/pkg
git -C /tmp/pkg log --oneline v3.9.4..v4.0.0
git -C /tmp/pkg log v3.9.4..v4.0.0 --grep='BREAKING' --format='%h %s%n%b'
git -C /tmp/pkg diff v3.9.4..v4.0.0 -- src/index.d.ts   # the public surface, in one diff
```

For a typed package, the diff of the type definitions is the most information-dense view
of the public API change that exists. Read it before the prose.

## Searching your own code

One search per breaking change, recorded with its hit count. A zero-hit search is a
result worth writing down — it is how you justify not doing work.

```bash
rg -n --stats 'removedFunction|OldClass\b' --glob '!node_modules' --glob '!vendor'
rg -n -tpy 'from pkg\.legacy import|pkg\.legacy\.'
rg -n --multiline 'client\.request\(\s*\{[^}]*retries'   # a default you now have to set explicitly
```

Search beyond the obvious tree:

- Test fixtures and snapshots, which encode the old output shape.
- Infrastructure and CI configuration, which pins versions of the same thing.
- Generated code and schemas, which are regenerated by a tool that has its own version.
- Documentation and examples, which are read by people and by whatever indexes them.
- Sibling services in other repositories that consume the same package, if the change
  crosses a wire format.

For a dynamic language, static search misses reflective access — `getattr`, dynamic
imports, string-keyed dispatch, dependency-injection containers, serialised class names
in a queue or a database. Grep for the symbol as a *string* as well as an identifier.

## Codemods and where they stop being trustworthy

Many large frameworks ship codemods, and they are worth running: `npx jscodeshift -t`,
`2to3`-style tools, `go fix`, `cargo fix --edition`, OpenRewrite recipes for Java.

Run them as their own commit, with no manual edits mixed in, so the review can be
"the codemod did this" rather than a diff of unknown provenance.

Where they stop being trustworthy:

- **They rewrite syntax, not intent.** A codemod that adds an explicit argument matching
  the old default is correct; whether the old default was what you wanted is a question
  it cannot ask.
- **They see one file at a time.** A wrapper you wrote around the old API is invisible to
  a codemod looking for direct call sites, and it is exactly where your remaining work is.
- **They skip what they cannot parse** — unusual syntax, generated files, templates — and
  the skip is often silent. Diff the file list the codemod touched against the file list
  your grep found, and investigate the difference.

Review a codemod diff by sampling rather than by reading all of it, and read every hunk
in the files your grep flagged as behaviour-sensitive.

## Pinning new behaviour with a test

For every behaviour change you find, write the test before the bump, against the current
version, asserting the *current* behaviour. Then run it after the bump. It fails, and the
failure is the change, in a place you chose, at a time you chose.

This is a characterisation test, not a correctness test: its job is to make a silent
change loud once. Keep the ones whose behaviour you care about, delete the rest in the
same change that lands the upgrade, and say which is which in the pull request. A
characterisation test kept by accident becomes a test that pins behaviour nobody chose.

## Compatibility shims

A shim is an adapter that presents the interface your code already uses on top of the new
dependency. It exists so the upgrade can land on main in one change while the call-site
migration happens in many.

```text
src/vendor/pkg-compat.ts     the shim: old signatures in, new library calls out
                             every function carries the upstream migration-guide link
                             and the ticket that deletes it
```

Rules that keep a shim from becoming permanent infrastructure:

- One module, one obvious name, and imports of the dependency allowed only from inside it.
  A lint rule or an import boundary check enforces this in a way a review does not.
- A deletion ticket at creation, and a comment naming it.
- No new functionality. The moment a shim gains behaviour of its own, deleting it stops
  being mechanical and it is permanent.
- A shim per upgrade, deleted before the next one. Two live shims for the same dependency
  means the first migration never finished.

## The audit artefact

The audit is a table, and it is the thing reviewers actually read:

```markdown
| Upstream change | Class | Sites | Signature change? | Fix | Test pinning it |
| --- | --- | --- | --- | --- | --- |
| render() removed, use createRoot | removed symbol | 3 | yes | codemod + manual in bootstrap | existing |
| sort() no longer stable | changed semantics | 11 | no | explicit tiebreak key at 4 sites | added, characterisation |
| fetch timeout defaults to 30s | changed default | 0 | no | none — we set it explicitly everywhere | n/a |
```

A row with zero sites is not noise. It is the evidence that a scary-looking upstream note
does not apply to you, and it is what stops the same investigation being repeated by the
next person.
