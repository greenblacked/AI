# Terraform idioms for modules that other people use

Terraform's failure mode is not a crash, it is a plan that quietly proposes to replace
something. Most of the practice below exists to keep the plan readable and its blast
radius small, because a mistake is measured in a destroyed database, not a stack trace.

## Module anatomy

```text
modules/artifact-bucket/
├── main.tf          # resources, one logical concern
├── variables.tf     # inputs, each with type, description, validation
├── outputs.tf       # what consumers may depend on
├── versions.tf      # required_version and required_providers
├── README.md        # generated by terraform-docs, not hand-maintained
└── examples/
    └── basic/       # a runnable call, used by CI and by humans reading the module
        ├── main.tf
        └── versions.tf
```

The `examples/` directory is not decoration: it is the only place a consumer sees a
complete call, and it is what CI runs `terraform validate` against.

## Version pinning

```hcl
# versions.tf
terraform {
  required_version = ">= 1.6.0, < 2.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.40"
    }
  }
}
```

`~> 5.40` accepts 5.41 and 5.99 but not 6.0. Providers change resource schemas across
majors, so an unbounded constraint means a plan that worked yesterday fails today on a
machine that ran `terraform init -upgrade`. Root configurations also commit
`.terraform.lock.hcl`, pinning exact provider versions and hashes per platform.

Shared modules get an exact reference — `?ref=v1.4.0` on a Git source, or an exact
registry `version` — because a floating reference means someone else's merge changes
your next plan.

A child module must not contain a `provider` block. Providers are configured in the root
and inherited; one defined inside a module cannot be removed cleanly (Terraform still
needs it at destroy time) and blocks the caller from passing an aliased provider for a
second region or account. Declare the requirement instead, adding
`configuration_aliases = [aws.replica]` to the `required_providers` entry when the module
genuinely needs a second, caller-supplied provider instance.

## Variables

Every variable gets a `type` and a `description`. The type turns "a list where a string
was expected" into a plan-time error rather than a failure three resources into an
apply.

```hcl
variable "bucket_name" {
  description = "Globally unique name for the artifact bucket."
  type        = string
  nullable    = false

  validation {
    condition     = can(regex("^[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]$", var.bucket_name))
    error_message = "bucket_name must be 3-63 chars, lowercase alphanumerics, dots or hyphens."
  }
}

variable "retention_days" {
  description = "Days to retain noncurrent object versions before expiry."
  type        = number
  default     = 30

  validation {
    condition     = var.retention_days >= 1 && var.retention_days <= 3650
    error_message = "retention_days must be between 1 and 3650."
  }
}

variable "kms_key_arn" {
  description = "Customer-managed KMS key. Null uses the AWS-managed S3 key."
  type        = string
  default     = null   # a considered default: null is a meaningful "use the platform key"
}
```

A `validation` block earns its place when it encodes a rule the provider would only
reject halfway through an apply — a name pattern, a range, a mutually exclusive pair.
One that merely restates the type is noise.

A default is right for anything with a safe, common value, and a bug when it decides
blast radius or cost: environment name, account or project id, production instance
class, whether deletion protection is on. There a missing value should stop the plan,
because a copy-pasted call that silently defaults to `dev` is how a change lands in the
wrong account. `nullable = false` belongs on any variable where `null` is not meaningful,
so a caller passing `null` from a conditional gets an error rather than the default.

`sensitive = true` stops the value appearing in CLI output and plan diffs. It encrypts
nothing: the value sits in plaintext in state, and everything derived from it becomes
sensitive too, which can make an otherwise useful plan unreadable. Better to keep the
secret out of Terraform — provision the secret manager entry, pass the ARN, and let the
application resolve it at runtime.

## Outputs

```hcl
output "bucket_arn" {
  description = "ARN of the artifact bucket, for IAM policy documents."
  value       = aws_s3_bucket.this.arn
}

output "db_password" {
  description = "Generated password. Also present in plaintext in state."
  value       = random_password.this.result
  sensitive   = true
}
```

Outputs are the module's public interface, so expose only what a consumer should be
allowed to depend on — every output someone starts using becomes a compatibility
constraint you did not intend to sign up for. Mark anything credential-shaped
`sensitive` so it is not echoed into a CI log by the caller's `terraform output`.

## Naming and tagging

Pick one naming scheme — `{project}-{environment}-{component}` is fine — and derive it in
`locals` so every resource in the module agrees. Tags go on the provider in the root
configuration rather than being repeated on each resource:

```hcl
provider "aws" {
  region = var.region

  default_tags {
    tags = {
      Environment = var.environment
      Owner       = var.owner
      ManagedBy   = "terraform"
    }
  }
}
```

`default_tags` belongs to the root because the module does not own the provider. Inside
the module, merge only tags that describe the resource itself.

## `for_each` over `count`

Use `count` only for a resource that is genuinely present or absent — a single toggle.
Use `for_each` for anything that is a set of things, because things get added and removed.

```hcl
resource "aws_iam_user" "this" {
  for_each = toset(var.usernames)
  name     = each.value
}
```

With `count`, addresses are positional: `[0]`, `[1]`, `[2]`. Remove the first name and
every later index shifts down, so Terraform plans to change user 0 from `alice` to `bob`,
user 1 from `bob` to `carol`, and destroy the last — destroying and recreating resources
nobody touched. Keyed by name, removing `alice` removes exactly
`aws_iam_user.this["alice"]`.

When refactoring from one to the other, tell Terraform where each resource went instead
of importing by hand:

```hcl
moved {
  from = aws_iam_user.this[0]
  to   = aws_iam_user.this["alice"]
}
```

`moved` blocks are checked at plan time and can be deleted once every environment has
applied them. They are the difference between a rename and an outage.

## `locals` and knowing when to stop

`locals` are for derived values used more than once — a computed name prefix, a merged
tag map, a filtered list. `try()` and `coalesce()` are useful for tolerating an optional
attribute, and corrosive when stacked: `try(coalesce(var.a, local.b), "")` hides which
input was wrong and turns a validation error into a silent empty string.

Resist wrapping a single resource in a module that passes twenty variables straight
through: it adds a version bump to every change, hides the provider documentation, and
gives a worse interface than the resource already had. A module earns its existence by
encoding a decision — a bucket that is always versioned, encrypted and logged — not by
renaming arguments.

## `lifecycle`

```hcl
resource "aws_lb_target_group" "this" {
  name = "${local.name_prefix}-tg"

  lifecycle {
    create_before_destroy = true    # the name is unique; the replacement needs to exist first
  }
}

resource "aws_db_instance" "this" {
  lifecycle {
    prevent_destroy = true          # a plan that would destroy this should fail, loudly
  }
}
```

`create_before_destroy` is required wherever a name-unique resource gets replaced, or the
destroy of the old and the create of the new deadlock on the name. `prevent_destroy`
belongs on anything holding data you cannot regenerate; it converts a bad plan into a
failed plan.

`ignore_changes` is a smell: it usually means something outside Terraform writes that
attribute — an autoscaler adjusting capacity, a pipeline updating an image tag, a tagging
robot — and unclear ownership is the real problem. Reserve it for the case where two
systems legitimately share a resource and you have written down which owns what.

## State

Use a remote backend with locking from the first commit, not after the first conflict:

```hcl
terraform {
  backend "s3" {
    bucket       = "org-terraform-state"
    key          = "prod/artifact-bucket/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true       # or dynamodb_table on older provider versions
  }
}
```

Split state one per environment and one per blast-radius domain — networking, data,
application. A single state for everything refreshes every resource on every apply, makes
plans slow enough that people stop reading them, and lets one bad apply reach production
while you were changing staging.

Treat the state file as a secret: it holds every attribute of every resource in
plaintext, including generated passwords and every `sensitive` variable. Encrypt the
bucket, restrict reads as tightly as deploy credentials, enable versioning so a corrupted
state can be rolled back, and never commit it or paste it into a ticket.

## Validation and testing

```bash
terraform fmt -check -recursive        # formatting; fails CI on a diff
terraform init -backend=false          # resolve modules and providers without touching state
terraform validate                     # types, references, required arguments
tflint --recursive                     # provider-specific rules, deprecated arguments
trivy config .                         # or: checkov -d . — misconfiguration scanning
terraform test                         # runs *.tftest.hcl
terraform-docs markdown table . > README.md
```

`terraform validate` needs an `init` first, and `-backend=false` lets it run in CI
without credentials or state access. Run the sequence against `examples/basic` as well as
the module root — that is what catches a required variable added without a default.

```hcl
# tests/defaults.tftest.hcl
run "creates_versioned_bucket" {
  command   = plan
  variables { bucket_name = "org-artifacts-test" }

  assert {
    condition     = aws_s3_bucket_versioning.this.versioning_configuration[0].status == "Enabled"
    error_message = "bucket versioning must default to Enabled"
  }
}
```

A `plan`-mode test needs no real infrastructure and still catches a refactor that
silently drops encryption or versioning.

## Worked module skeleton

```hcl
# versions.tf — as in "Version pinning" above

# variables.tf
variable "name_prefix" {
  description = "Prefix for all resource names, typically {project}-{environment}."
  type        = string
  nullable    = false

  validation {
    condition     = can(regex("^[a-z][a-z0-9-]{1,32}$", var.name_prefix))
    error_message = "name_prefix must be lowercase alphanumerics or hyphens, 2-33 chars."
  }
}

# main.tf
resource "aws_s3_bucket" "this" {
  bucket = "${var.name_prefix}-artifacts"

  lifecycle {
    prevent_destroy = true
  }
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_public_access_block" "this" {
  bucket                  = aws_s3_bucket.this.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# outputs.tf
output "bucket_arn" {
  description = "ARN of the artifact bucket, for IAM policy documents."
  value       = aws_s3_bucket.this.arn
}
```

The secure defaults live in the module rather than in a consumer's checklist: public
access blocked, versioning on, destroy prevented. That is the decision the module exists
to encode, and the reason to use it instead of writing the resources by hand each time.
