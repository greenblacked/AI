## Recognising the owner of resolv.conf

| What you see | Owner | Upstream servers are in |
| --- | --- | --- |
| Symlink to `/run/systemd/resolve/stub-resolv.conf`, `nameserver 127.0.0.53` | systemd-resolved, stub mode | `resolvectl status`, `/run/systemd/resolve/resolv.conf` |
| Symlink to `/run/systemd/resolve/resolv.conf` | systemd-resolved, direct mode | The file itself |
| Header "Generated by NetworkManager" | NetworkManager writing the file | `nmcli device show IFACE`, `nmcli connection show NAME` |
| Symlink to `/run/resolvconf/resolv.conf` | resolvconf, fed by hooks | `/etc/resolvconf/resolv.conf.d/` and interface hooks |
| Header "Generated by dhclient" or `dhcpcd` | The DHCP client | The lease file |
| Plain file, never changes | Static | The file |
| Plain file that reverts | A manager overwriting it | Find with `journalctl -b \| grep -i resolv` and the manager's config |
| Container, bind-mounted from the host or generated by the runtime | The container runtime or orchestrator | The runtime's DNS options, the pod DNS policy |

To see whether systemd-resolved is the active resolver: `systemctl is-active systemd-resolved`.

## Where each owner keeps its settings

- **systemd-resolved global:** `/etc/systemd/resolved.conf` and drop-ins in `/etc/systemd/resolved.conf.d/` (`DNS=`, `FallbackDNS=`, `Domains=`, `DNSSEC=`, `DNSStubListener=`). Restart the service after editing. Per-link settings come from the network manager.
- **systemd-networkd:** the `.network` file's `[Network]` section: `DNS=`, `Domains=` (a leading `~` makes a routing domain), and `UseDNS=` for DHCP-supplied servers. `networkctl reload` applies.
- **NetworkManager:** per connection, `nmcli connection modify NAME ipv4.dns "10.0.0.2" ipv4.dns-search "corp.example" ipv4.ignore-auto-dns yes`, then `nmcli connection up NAME`. A routing-only domain is written with the tilde in `ipv4.dns-search`, as `~corp.example`. NetworkManager's `dns=` option (`default`, `systemd-resolved`, `none`) in `/etc/NetworkManager/conf.d/` decides whether it writes the file, hands servers to resolved, or leaves it alone.
- **netplan:** `nameservers:` with `addresses:` and `search:` under the interface, then `netplan apply` on a host where a brief network interruption is acceptable. Netplan renders for networkd or NetworkManager, so the setting still ends up in one of the two above.
- **cloud-init:** network configuration is regenerated at boot from instance metadata, so a hand edit of the rendered file is overwritten at the next boot; change the cloud-init network config, or disable its network management only as a deliberate decision.

## Split DNS for a VPN

Goal: names under the corporate suffix go to the corporate resolver on the VPN link, and everything else goes to the normal link.

```bash
resolvectl status                                        # find the VPN link name
resolvectl dns tun0 10.8.0.2                             # runtime: servers for the VPN link
resolvectl domain tun0 ~corp.example ~10.in-addr.arpa    # runtime: routing domains
resolvectl query app.corp.example                        # confirm the link that answered
resolvectl query www.example.org                         # confirm the other link answers public names
```

`tun0` and the addresses are examples; use the real link and servers. The `~` marks a routing domain, and adding the reverse zone makes PTR queries for that range follow too. Remember these commands change the running state only. For a lasting setup put `DNS=` and `Domains=~corp.example` in the VPN client's network configuration or the connection profile, and `resolvectl revert tun0` to clear the runtime override while testing. If the VPN client itself writes `/etc/resolv.conf` directly, it bypasses resolved: look for an update script and make it call resolved (`resolvectl`) rather than the file.

A leading `~.` on a link sends all names there; give that to one link only, and only when the intent is to send all queries through the tunnel.

## Clearing caches

```bash
resolvectl flush-caches            # systemd-resolved
resolvectl reset-server-features   # forget learned per-server capability downgrades (EDNS, DNSSEC)
nscd -i hosts                      # nscd, where it is installed
sss_cache -E                       # sssd, where it is installed
```

The second one matters after a flaky upstream: resolved remembers that a server failed with EDNS or DNSSEC and keeps using the degraded mode until it is reset. For dnsmasq, send it SIGHUP or restart it. After flushing, query again with `resolvectl query NAME` and read the fresh answer. A negative answer is held for the SOA's negative TTL on any caching resolver you do not control, so the fix may be correct and still invisible until it expires.

## Application-specific resolvers

- **Go** programs may use the pure Go resolver, which reads `resolv.conf` and `nsswitch.conf` itself, or the cgo resolver that calls the C library. Setting `GODEBUG=netdns=2` prints which one is used and its choices; `netdns=cgo` or `netdns=go` forces one for a test.
- **Java** caches successful lookups for the JVM's configured TTL, and may cache for the process lifetime under a security manager; check `networkaddress.cache.ttl` and `networkaddress.cache.negative.ttl`.
- **Node.js** `dns.lookup` uses the C library (a thread pool call), while `dns.resolve*` talks to the nameservers directly; the two can disagree on the same host for the same reasons `getent` and `dig` do.
- **Containers** read the container's own `/etc/resolv.conf`, usually generated by the runtime; read it from inside (`cat /etc/resolv.conf` in the container), not on the host.
