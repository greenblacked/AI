# Credentials, factors and recovery

Read this when you own the credential rather than delegating it to an identity provider:
you are storing passwords, enrolling factors, or designing the path back in for a user who
has lost one. It is the depth behind steps 7 and 8 of `SKILL.md`.

Parameter values age faster than anything else in this repository. Every figure below is
attributed to a document with a date, and the ones that come from continuously revised
pages say so. Read the current revision before committing a number to your own design
document, and record in that document which revision you read.

## Password hashing

Use a memory-hard function with a per-password salt generated by the library, in this
order of preference:

| Algorithm | Primary source | Notes |
| --- | --- | --- |
| Argon2id | RFC 9106 (September 2021) | First choice. The RFC gives two recommended configurations, a high-memory one and a lower-memory one with more passes, and describes how to tune memory, iterations and parallelism for your hardware. |
| scrypt | RFC 7914 (August 2016) | Acceptable where Argon2id is unavailable. Memory-hard, and the cost parameter is the one that matters. |
| bcrypt | Niels Provos and David Mazieres, USENIX 1999 | Acceptable, and widely available. Raise the work factor over time. |
| PBKDF2-HMAC-SHA256 | NIST SP 800-132 (December 2010) | The choice when a certification requires a NIST-approved function. Not memory-hard, so it is the weakest of the four against dedicated hardware, and needs a high iteration count. |

For current minimum parameter values, the OWASP Password Storage Cheat Sheet is the source
practitioners actually use, because it is revised as hardware moves and an RFC is not.
It is a continuously updated page rather than a dated publication, so read the revision
date printed on it and cite that date. Whatever it says, tune against your own hardware:
pick the highest cost your authentication endpoint can absorb at peak login rate with
headroom, measure it, and put the measurement and the date in the design document so the
next person knows when it was last true.

Three details that cause real incidents:

- **bcrypt truncates its input at 72 bytes.** A long passphrase is silently shortened, and
  some implementations also terminate at a null byte. Where you pre-hash to work around
  this, base64-encode the digest before passing it in, because a raw digest can contain a
  null byte and reintroduce the truncation you were fixing.
- **A fast hash is a defect, not a weak choice.** Salted SHA-256, one pass of anything from
  the SHA family, or a hand-rolled iteration loop. The entire mechanism is making each
  guess expensive against hardware better than yours, and a fast hash concedes it.
- **A pepper is an addition, not a substitute.** A secret key held outside the database and
  mixed in — ideally as an HMAC over the password before hashing, or by encrypting the
  stored hash — helps when the dump leaks and the key does not. It does nothing about the
  work factor, and it creates a key whose loss locks out every user, so design the rotation
  before adopting it.

## Password policy

NIST SP 800-63B, Digital Identity Guidelines: Authentication and Lifecycle Management,
Revision 3 (June 2017, incorporating the errata update of March 2020), sets out the
memorized-secret rules in its section 5.1.1. The substance, which is what to implement:

- **Length is the requirement; composition is not.** Enforce a minimum length, allow long
  passphrases, accept every printable character including spaces and Unicode, and do not
  impose "one uppercase, one digit, one symbol" rules. Composition rules produce a small
  number of predictable transformations of one remembered word.
- **Check the candidate against a list of compromised values** at registration and at every
  change, and reject a match. This is the control that composition rules were a poor proxy
  for: it rejects the passwords that are actually guessed first. Use a published breach
  corpus, a range-query service that does not receive the password itself, or a local copy,
  and add context-specific terms — your product name, the user's email local part, the
  company name.
- **No periodic expiry.** Forced rotation on a calendar produces incremental mutations and
  drives users to reuse. Force a change on evidence of compromise instead.
- **Allow paste, and allow the password manager.** Blocking paste selects against the users
  with the strongest passwords.
- **Do not use password hints or knowledge-based questions.** Both are recoverable from
  public information and from the user's own social accounts.

Check whether a later revision of SP 800-63B supersedes Revision 3 before quoting a
specific number from it; the guidance above is stable across revisions, but the parameter
values are exactly the part that changes.

OWASP ASVS, Authentication chapter — V2 in version 4.0.3 (October 2021), renumbered in the
5.x line — carries the same rules as testable requirements, which is the more useful form
when someone has to verify the implementation. Cite the requirement text rather than the
number unless you know which version your reader holds.

## Migrating an existing weak hash

You will inherit MD5, unsalted SHA-1, or bcrypt at a work factor set in 2014. You cannot
recompute a strong hash without the plaintext, so there are two honest routes:

1. **Upgrade on next login.** When a user authenticates successfully against the old hash,
   immediately rehash the plaintext you just verified with the new algorithm and replace
   the record. Track the proportion migrated, and set a date after which the remainder are
   forced through a reset. This is the path with no user impact for active users.
2. **Wrap the old hash.** Store the new function applied to the old digest — for example
   Argon2id over the existing SHA-1 output — which upgrades every record at once without
   any plaintext. Record the scheme per row so verification knows which path to take, and
   unwrap opportunistically at next login. Useful when a breach makes waiting unacceptable.

Either way, version the stored hash so the record says which algorithm and parameters
produced it. A password table with no scheme column is the reason these migrations get
postponed.

## Multi-factor: what resists phishing and what does not

The split that decides the choice:

| Factor | Guessing | Phishing | Detail |
| --- | --- | --- | --- |
| Passkeys and security keys | Resistant | Resistant | W3C Web Authentication (WebAuthn) Level 2, W3C Recommendation, 8 April 2021. The credential is scoped to the relying party identifier and the assertion covers the origin, so a look-alike domain cannot obtain anything usable. There is no code for the user to read out and therefore nothing to relay. |
| Smartcard or client certificate | Resistant | Resistant | The same property through a different mechanism. Common where a certificate estate already exists. |
| TOTP authenticator app | Resistant | Not resistant | RFC 6238 (May 2011), built on HOTP, RFC 4226 (December 2005). The user reads a code and types it wherever they were asked to, which is the whole of the weakness. |
| Push approval with number matching | Resistant | Not resistant | Number matching addresses approval fatigue, where a user taps to stop the notifications. It does not address a relay, because the user is approving a real prompt for a session they did not start. |
| SMS or voice one-time code | Partly | Not resistant | Also exposed to number porting and to interception. SP 800-63B Revision 3 treats public-telephone-network delivery as a restricted authenticator, requiring a documented risk assessment and a migration plan. |
| Email one-time code or magic link | Partly | Not resistant | The account's strength becomes the mailbox's strength, which is usually a different provider's problem. |
| Backup codes | Resistant | Not resistant | Necessary for recovery; treat each as a password, rate-limit them, and invalidate the set on regeneration. |

Why the split decides rather than informs: credential phishing at scale runs through a
relay that sits between the user and the real site and forwards both directions in real
time. Every factor in the "not resistant" column passes through it, because a code the
user can read out is a code the relay can forward inside its validity window. Only a factor
bound to the origin by the browser or the platform breaks that, because the assertion
produced for the look-alike domain is not valid for yours.

The practical policy: require a phishing-resistant factor for administrators, for anyone
who can reach bulk customer data, and for anyone who can change the authentication system
itself. Offer passkeys to everyone and drive adoption. Accept TOTP as the fallback, since a
second factor of any kind defeats credential stuffing, which is the volume attack. Retire
SMS as a factor before retiring it as a recovery channel, and be honest in the design about
which of the two you have actually done.

One more thing the login-time factor does not cover: a session token stolen after
authentication is unaffected by how strong the login was. That is the argument for short
sessions, for sender-constrained tokens, and for re-authentication at the operations that
matter.

## Enrolment and step-up

Enrol a second factor at registration, or at the first sign-in, rather than offering it in
a settings page most users never open. The choice is between making it a step in the flow
everyone completes and accepting single-digit adoption.

Require at least two factors at enrolment where you can — a passkey plus a backup code, or
two passkeys on different devices — so that losing one device is not an account recovery
event. Most account recovery weakness traces back to a single enrolled factor.

Step-up: rather than shortening every session to protect a handful of operations, require a
fresh authentication immediately before the dangerous ones — changing a payout destination,
exporting a customer table, adding an administrator, disabling audit logging, changing the
recovery email or the enrolled factors. In OpenID Connect terms this is `prompt=login` or a
`max_age`, with `auth_time` checked in the response; locally it is a re-prompt with a short
validity window recorded on the session. Say in the design which operations require it.

## Account recovery

Recovery is the real strength of the design, because it is a path to the account that
bypasses every factor. Two rules:

1. **The recovery path cannot be weaker than the factor it can reset.** An account secured
   by a security key and recoverable by an emailed link is secured by that mailbox.
2. **Design it explicitly, or it will be designed under pressure** by whoever is handling
   the locked-out customer, and it will become a support process with no controls.

What tends to work: backup codes issued at enrolment and stored by the user; a second
enrolled device; for a workforce, an in-person or video verification with a delay; for a
consumer product, a recovery flow with a waiting period, notification to every registered
channel, and a hold on sensitive operations for some days after recovery.

What tends to fail: knowledge-based questions, a support agent who can reset a factor
without verification and under pressure to be helpful, and recovery to an address or number
that was changed recently. Enforce a delay after a change to a recovery channel before that
channel can be used for recovery — this one rule closes a large fraction of real takeovers.

Notify on every one of: recovery initiated, recovery completed, factor added, factor
removed, password changed, email changed. Send to the old address as well as the new. The
notification is often the only signal a user gets that any of this happened.

## Throttling, lockout and enumeration

**Enumeration.** Identical response for "no such account" and "wrong password" — same
status code, same body, same timing. Timing is the one that leaks in practice, because an
unknown account returns before any hash comparison runs; compare against a dummy hash of
the same cost so the two paths take the same time. Password reset answers "if that address
has an account, a link is on its way" regardless. Registration cannot be fully closed,
because "that address is already registered" is something the user needs to know; bound it
with rate limiting, and where the risk justifies it, complete the signal by email rather
than in the response body.

**Throttling over lockout.** A lockout threshold turns a username list into a denial of
service: an attacker with a leaked email list locks out the whole user base at trivial
cost, and the resulting outage looks like an infrastructure failure while the support queue
becomes the incident. Throttle instead:

- Exponential backoff per account on consecutive failures, with the delay reported as a
  generic "try again later" rather than a countdown that confirms the account exists.
- A separate control per source address, understanding that it is weak on its own —
  distributed stuffing uses many addresses and one attempt each.
- A global control that recognises the pattern per-account counters cannot see: a low rate
  of failures spread across a large number of accounts, which is credential stuffing rather
  than a targeted guess. Alert on the ratio of failed to successful logins as a whole, not
  only on individual accounts.
- Where a lock is genuinely required by policy, make it short, self-clearing, and paired
  with a way back in that does not need a human.

SP 800-63B Revision 3 sets the ceiling at 100 consecutive failed attempts and requires an
effective throttling mechanism, which is the standards-side version of the same argument.

Also rate-limit the endpoints people forget: password reset requests, MFA code submission
and resend, registration, and the token endpoint. An unthrottled MFA verification endpoint
makes a six-digit code guessable, which quietly removes the factor.

## Verification

- Two user accounts, one existing and one not: identical status, body and response time on
  a failed login.
- A password on any public breach list is rejected at registration and at change.
- The stored hash's algorithm and parameters match what the design document says, read from
  a record rather than from the code.
- A user with MFA enrolled cannot bypass it through the reset flow.
- Changing the recovery email does not immediately enable recovery through the new address.
- The MFA verification endpoint is rate-limited: confirm it blocks well before the code
  space is exhausted.
- Password change ends other sessions, and every one of the notification events above
  actually sends.
