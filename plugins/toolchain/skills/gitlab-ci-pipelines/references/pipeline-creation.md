# Pipeline creation, rules and composition

Contents: workflow rules, rules evaluation, needs, include and extends, child pipelines.

Verify every keyword against the GitLab documentation for the version in use. Behaviour
of `rules:changes`, `needs:` and `include:` has changed across releases.

## workflow:rules

One policy: merge request pipelines, plus the default branch and tags.

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG
```

The second rule stops the branch pipeline when a merge request is open for that branch,
which removes the duplicate. A branch with no merge request yet creates no pipeline under
this policy; add a final `- if: $CI_COMMIT_BRANCH` rule if feature branches need one.

Predefined variables differ by pipeline type. `$CI_COMMIT_BRANCH` is unset in a merge
request pipeline, and `$CI_MERGE_REQUEST_SOURCE_BRANCH_NAME` is set only there. A rule on
the wrong one never matches, and the job silently disappears.

## Rules evaluation

- The first matching rule wins. Order `when: never` exclusions first.
- A job with no matching rule is not created. With a rule that matches and sets no
  `when`, the default is `on_success`.
- A rule list that ends without a catch-all excludes everything else; write the intent.
- `rules:if` uses variable expressions; an undefined variable is empty, so a typo in a
  variable name makes the rule false without an error.
- `rules:changes` needs a comparison base. Check `changes:compare_to` and the behaviour
  for new branches and tags in the docs for the pinned version.
- `rules:variables` sets a variable only for the matching rule, which is how one job
  serves two environments.

## needs

- `needs:` ignores stage ordering for start time and downloads artifacts of only the
  listed jobs. `needs: []` starts a job immediately with no artifacts.
- A `needs:` target that was not created (excluded by rules) fails the pipeline creation
  unless the entry sets `optional: true`.
- `needs:` across pipelines (`needs:pipeline`) and with a child pipeline's artifacts have
  their own syntax; read the documentation before using either.
- Check the documented maximum number of `needs:` entries per job for your version.

## include, extends, !reference

- `include:project` and `include:component` take a `ref`/version. Pin to a tag or full
  SHA; a branch ref changes every consumer when it moves.
- `include:local` resolves in the pipeline's own project; `include:remote` fetches a URL
  and is a supply-chain dependency with no pin.
- `extends:` merges maps deeply but replaces arrays; a child `script:` or `rules:`
  replaces the parent's. Use `!reference [.parent, script]` inside the child's array to
  keep the parent's items.
- Variables defined in an included file are overridden by the including file's, in that
  order; check precedence in the docs when a value is not what the file shows.
- Order does not matter for hidden jobs; an `extends:` of a missing job fails creation.

## Child and multi-project pipelines

- `trigger:include` starts a child in the same project from a file or an artifact
  generated by an earlier job (dynamic child pipelines). The trigger job's own `rules:`
  decide whether it exists.
- `trigger:project` starts a pipeline in another project, using that project's own
  `workflow:rules`, and requires the triggering user to have access.
- A trigger job forwards its YAML variables, including global `variables:`, by default
  (`trigger:forward:yaml_variables`, true). Pipeline variables (manual, API, schedule) are
  not forwarded unless `forward:pipeline_variables: true`. Use `inherit:variables` to stop
  global ones. Check the `forward:` options in the docs for the pinned version.
- `trigger:strategy: depend` makes the trigger job mirror the downstream status;
  without it the parent can go green while the child fails.
- A child pipeline cannot be re-run on its own from the parent's retry in every version;
  check the documented retry behaviour before depending on it.
